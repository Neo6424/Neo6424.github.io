> **2026-11-24 교차 검토:** 과기정통부의 3,367만 3,817건은 내 정보 수정 페이지의 이름·이메일 기록이며 배송지 페이지의 약 1억 4천만 회는 조회 횟수다. 개인정보위는 약 3,322만 회원과 약 433만 제3자의 정보 유출을 발표했다. 각각의 집계 대상과 기준은 다르다. 과징금 총액 6,246억 8,100만 원은 유출 관련 4,235억 7,500만 원과 별도의 행태정보 위반 2,011억 600만 원을 합친 금액이다. 과기정통부가 확인한 무단 접속 기간은 2025-04-14~2025-11-08이며 정부 조사 발표는 2026-02-10이다. 이 프로젝트는 조사·공개 시점을 기준으로 선정했다. [과기정통부 조사](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng) · [개인정보위 조사](https://pipc.go.kr/eng/user/ltn/new/noticeDetail.do?bbsId=BBSMSTR_000000000001&nttId=3071)

- **조사결과**: 2026-02-10(과기정통부 민관합동조사단)

## 1. TL;DR

- 쿠팡의 **전 직원(개발자)**이 퇴사 후에도 무단 접속해 고객 개인정보 3,367만여 건을 유출하고, 성명·전화번호·주소가 담긴 배송지 목록 페이지를 약 **1억 4천만 회** 조회했다.
- 근본 원인은 고도의 해킹이 아니라 **인증 체계의 설계 결함**이었다. **서명키 관리와 폐기**가 미흡했고, 관문(Gateway) 서버에서는 위조된 전자 출입증의 정상 발급 여부를 검증하는 체계가 부족했다. 즉 로그인 없이 토큰을 위조해 남의 계정으로 들어갈 수 있었다.
- 사고 자체보다 **대응이 더 문제**였다. 자체 조사에서 저장된 자료를 약 3천 건으로 발표했으나 정부는 무단 조회된 정보의 범위를 더 넓게 판단했고, 자료 보전 명령을 어겨 로그가 삭제됐으며, 72시간 통지 의무를 어기고 개인정보 보호책임자(CPO)를 배제한 채 해커 진술에만 의존해 조사 결과를 냈다. 결국 6,200억 원대 과징금으로 이어졌다.

## 2. 사건 개요

쿠팡 침해사고는 외부의 정교한 해킹이 아니라 **내부 사정을 아는 퇴직자**가 허술한 인증 구조를 악용한 사건이다. 공격자는 쿠팡의 개발자였던 전 직원으로, 서비스 인증에 사용되는 서명키를 알고 있었다.

과학기술정보통신부 민관합동조사단은 쿠팡 웹 접속 기록(로그) 25.6TB 분량(약 6,642억 건)을 분석해, '내 정보 수정 페이지'에서 성명·이메일 등 **3,367만 3,817건**의 유출을 확인했다. 또한 성명·전화번호·주소가 담긴 '배송지 목록' 페이지 조회가 약 **1억 4,800만 회**에 달했다. 공격자가 유출 정보를 해외 클라우드 서버로 전송할 수 있는 기능도 확인됐으나, 실제 전송 여부는 기록이 남지 않아 규명하지 못했다.

이후 개인정보보호위원회 조사에서 회원 약 3,300만 명, 비회원 최소 430만 명의 정보가 유출된 것으로 집계됐고, 쿠팡에 **과징금 6,246억 8,100만 원** 등이 부과됐다. 이 총액에는 유출 방지 소홀뿐 아니라 별도의 행태정보 수집 관련 위반도 포함된다. [개인정보위 설명](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS210&mCode=C020020000&nttId=12612)

## 4. 배경 지식

### 토큰 기반 인증과 서명키

일부 웹 서비스는 로그인 후 서명된 토큰을 발급하고 이후 요청에서 이를 검증한다. 대칭키 방식에서는 같은 비밀키로 서명과 검증을 수행하고, 비대칭키 방식에서는 개인키로 서명하고 공개키로 검증한다. 어느 방식이든 서명에 필요한 비밀키를 안전하게 관리해야 한다.

이 구조의 안전성은 전적으로 **서명키의 비밀 유지**에 달려 있다. 서명키가 유출되면 공격자는 "나는 아무개다"라고 적은 토큰을 직접 만들어 서명할 수 있고, 서버는 그 토큰을 정상으로 받아들인다. 로그인 절차 자체가 무의미해지는 것이다.

### 키는 어디에 보관해야 하나

서명키 같은 비밀 값은 소스코드와 분리해 **전용 비밀 저장소(KMS·HSM·Secret Manager 등)**에 넣고, 주기적으로 교체(rotation)해야 한다. 소스코드에 직접 적어 넣는 **하드코딩(hard-coding)**은 가장 기초적인 안티패턴이다. 코드 저장소 접근 권한이 있는 사람이라면 누구나, 심지어 퇴사 후에도 키를 알 수 있기 때문이다.

## 5. 공격 흐름 분석

정부가 공개한 자료는 서명키, 사용자 고유번호, 위조 전자 출입증과 접속 로그의 관계를 설명한다. **쿠팡의 실제 인증 소스코드, 공격 스크립트 전문, 토큰 필드명과 서명 알고리즘은 이 글의 근거 자료에서 확인되지 않는다.** 아래 의사코드는 취약한 신뢰 관계를 설명하기 위해 작성한 예시이며 실제 코드나 공격 페이로드가 아니다. [과기정통부 조사](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng) · [정부 브리핑](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156744092&pWise=main&pWiseMain=L5)

### 5-1. 출발점: 퇴사 후에도 유효한 서명키

조사단에 따르면 공격자는 재직 당시 이용자 인증 체계를 개발·관리하며 알게 된 서명키와 내부 정보를 퇴사 후 악용했다. 개인정보위는 회사가 해당 키를 즉시 갱신하거나 폐기하지 않았고, 필요하지 않은 상황에서도 서명키를 평문으로 볼 수 있었다고 밝혔다.

과기정통부는 별도로 재직 중인 개발자 노트북에서 키가 하드코딩을 통해 로컬에 저장된 사실을 확인했다. 이 사실만으로 공격자가 **그 노트북 또는 특정 소스 파일에서 직접 키를 빼냈다**고 결론 내릴 수는 없다. [개인정보위 조사](https://pipc.go.kr/eng/user/ltn/new/noticeDetail.do?bbsId=BBSMSTR_000000000001&nttId=3071)

### 5-2. 다른 이용자의 토큰을 만드는 방식

정상적인 경우 서비스는 로그인을 확인한 다음 이용자를 식별하는 인증 정보를 발급한다. 조사단은 문제의 토큰에 이용자 고유번호가 포함되고 공격자가 접근할 때마다 번호를 넣어 토큰을 새로 만들었다고 설명했다.

다음은 서명키 노출이 왜 위험한지 나타내는 **독립적인 의사코드**다. 이름과 구조는 설명용으로 정했으며 실제 쿠팡 토큰 형식이나 알고리즘을 재현한 것이 아니다.

```text
# 개념 예시 — 실제 쿠팡 코드 아님
claims = { "user_id": target_user_id }
forged_token = sign(claims, compromised_signing_key)
send_request(forged_token)
```

1. 공격자는 내부 구조를 이용해 대상 이용자의 고유번호를 토큰 내용에 넣는다.
2. 이미 확보한 서명키로 그 내용을 서명해 정상 발급처럼 보이는 토큰을 만든다.
3. 토큰을 요청에 실어 보내면, 서명 자체는 유효하므로 검증 서버가 정상 토큰과 구분하기 어려워진다.

키와 고유번호를 공격자가 어떻게 결합했는지의 개념은 공식 조사에서 확인된다. 다만 실제 코드의 변수명, 토큰 종류·필드, 서명 방식과 공격자가 사용한 함수명까지는 이 자료로 특정하지 않는다. [정부 질의응답](https://www.korea.kr/briefing/policyBriefingView.do?newsId=156744092&pWise=main&pWiseMain=L5)

### 5-3. 인증 관문에서 무엇이 빠졌나

관문 서버가 서명을 검사하는 것은 토큰이 해당 키로 만들어졌는지 확인하는 과정이다. **서명키가 유출된 경우에는 서명이 맞아도 정상 로그인으로 발급된 토큰이 아닐 수 있다.** 조사단은 정상 발급 절차를 거친 전자 출입증인지 확인하는 체계가 부족했다고 설명했다.

```text
# 개념 예시 — 실제 쿠팡 코드 아님
if signature_is_valid(token):
    allow_access_to_claimed_user()
```

위 예시는 서명 확인만으로 정상 발급 여부를 구분하기 어려운 신뢰 경계를 보여준다. 쿠팡 서버가 위와 같은 소스코드를 사용했다는 주장은 아니다. 서버 측 세션·발급 이력 확인이나 키의 사용 범위 제한은 위험을 줄이는 설계 방안이지만, 어떤 방식이 적합한지는 서비스 구조에 따라 달라진다.

### 5-4. 반복 요청과 유출 범위

정부 조사에 따르면 공격자는 자동화된 웹 크롤링 도구와 여러 IP를 이용해 계정 정보·배송지·주문 내역에 접근했다. 조사단은 접속 로그를 고유번호, IP, 접속 경로와 대조해 범위를 추정했다.

```text
위조 인증 정보 생성
  → 정상 로그인 없이 관문 통과
  → 이용자별 정보 페이지 요청 반복
  → 페이지 접근 로그를 분석해 피해 범위 추정
```

정부는 내 정보 수정 페이지의 이름·이메일 33,673,817건, 배송지 목록 페이지 148,056,502회 접근을 확인했다. **건수와 접근 횟수는 단위가 다르며**, 배송지 목록의 접근 횟수를 고유 피해자 수로 해석해서는 안 된다. 조사단은 외부 서버 전송 기능이 있는 스크립트도 확인했지만, 해당 기능이 실제 실행돼 어디로 전송됐는지는 확보된 기록만으로 확정하지 못했다. 공격자가 샘플 정보를 이메일로 보낸 사실은 이와 별개로 확인됐다. [과기정통부 조사](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng)

### 5-5. 코드 수준의 개선 방향

- 서명키를 소스코드와 개발자 단말에서 분리하고, 평문 접근과 서명 권한을 최소화한다.
- 퇴사·노출 의심 때 영향을 받는 키를 식별해 안전하게 교체하고, 기존 인증 정보의 무효화 범위를 점검한다.
- 토큰의 서명뿐 아니라 필요한 경우 발급 이력·세션 상태를 대조해 유효한 서명을 가진 위조 토큰의 위험을 줄인다.
- 대량 계정 조회와 이상 요청을 탐지하고 로그를 별도 저장소에 보전한다.

이는 실제 쿠팡 수정 코드가 아니라 조사 결과를 바탕으로 한 설계 제안이다.

## 6. 근본 원인 분석

### 코드로 보는 원인: 서명키 관리와 정상 발급 확인

과기정통부는 개발자 단말에 서명키가 하드코딩을 통해 저장된 사례와, 정상 인증 절차를 거쳐 발급된 전자 출입증인지 확인하는 체계의 부재를 발표했다. **실제 쿠팡 소스코드와 서명 알고리즘은 조사 결과에 공개되지 않았다.** 따라서 아래는 원리를 설명하려고 별도로 만든 예시이며 사고 당시 코드나 공격자 스크립트가 아니다. [과기정통부 조사 결과](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng)

```python
# 설명용 예시: 실제 쿠팡 코드·키·토큰 형식이 아님
SIGNING_KEY = "example-secret-in-source"

def authenticate(token):
    claims = verify_signature(token, SIGNING_KEY)
    if claims is None:
        return deny()
    return allow_as(claims["user_id"])
```

이 예시의 첫 번째 문제는 서명키가 코드에 들어 있다는 점이다. 소스코드, 백업, 개발자 단말 등에 키가 복제되면 접근했던 사람이 퇴사하더라도 키를 기억하거나 보관할 수 있다. 계정만 비활성화해도 이미 알려진 공유 키는 바뀌지 않는다. 실제 사건에서도 개인정보위는 퇴사 후 관련 키를 즉시 갱신·폐기하지 않은 점을 지적했다.

두 번째 문제는 예시의 authenticate가 **서명 확인만 성공하면** 토큰 속 user\_id를 받아들인다는 것이다. 서명키를 가진 공격자는 타인의 고유번호로 새 토큰을 만들 수 있으므로, 유효한 서명은 정상 로그인 절차를 거친 발급 사실까지 증명하지 않는다. 정부가 확인한 문제도 정상 발급 여부를 검증하는 체계가 부족했다는 것이며, 위와 같은 구체적인 함수·분기 구조가 실제로 사용됐다는 뜻은 아니다. [개인정보위 조사](https://pipc.go.kr/eng/user/ltn/new/noticeDetail.do?bbsId=BBSMSTR_000000000001&nttId=3071)

### 개선 방향을 보여주는 설계 예시

```text
# 설명용 의사코드: 실제 쿠팡 수정 코드 아님
claims = verify_signature_and_expiry(token, active_key)
session = issued_session_store.lookup(claims.session_id)
if session is missing or session.revoked:
    deny()
if session.user_id != claims.user_id:
    deny()
allow_as(session.user_id)
```

서명과 유효기간을 확인한 뒤 서버가 실제 발급한 세션인지, 폐기됐는지, 사용자와 연결되는지 확인하는 방식의 예시다. 서버가 발급 이력을 안전하게 보관하고 공격자가 유효한 다른 세션을 탈취하지 않았다는 조건이 필요하다. 키가 이미 유출됐다면 이런 검증을 더하는 것만으로 충분하지 않으며 **노출 키 교체·폐기와 기존 토큰의 영향 범위 점검**을 병행해야 한다. 발급 이력 기반 검증은 가능한 설계 중 하나로, 실제 쿠팡이 이 코드를 적용했음을 뜻하지 않는다.

### 6-1. 기술적 원인

- **서명키 관리 부실**: 개인정보위는 필요하지 않은 경우에도 대체 서명키에 평문으로 접근할 수 있었고 퇴사 후 즉시 갱신·폐기하지 않았다고 밝혔다. 과기정통부는 재직 중인 개발자의 노트북에서 하드코딩을 통한 키의 로컬 저장을 확인했다. 다만 이것이 공격자의 구체적인 키 취득 경로임이 입증된 것과는 구분해야 한다. [과기정통부 조사](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng)
- **키 갱신·폐기 미흡**: 퇴사 후 노출 가능성이 있는 키가 즉시 갱신·폐기되지 않았다. 하드코딩이 유일한 원인이었다고는 단정할 수 없다.
- **위조 토큰 검증 미흡**: 조사단에 따르면 정상 발급된 출입증인지 검증하는 체계가 부족했다. 추가 세션·기기·행위 검증의 구체적 적용 범위는 공개 자료만으로 단정하지 않는다.
- **이상 행위 탐지 부재**: 위조 인증을 이용한 대량 조회를 조기에 탐지·차단하지 못했다. 1억여 회는 전체 조회 횟수이며 한 계정의 조회 횟수로 확인된 것은 아니다.

### 6-2. 관리적·조직적 원인

- **퇴사자 권한 회수 미흡**: 퇴직자가 아는 비밀이 그대로 살아 있는, 오프보딩 프로세스의 공백.
- **기본 안전조치 소홀**: 정부는 "고도의 해킹 기술이 아니라 기본적인 안전관리 체계가 미흡했기 때문"으로 결론지었다.

## 8. 미흡했던 점

- **발표 범위의 차이**: 쿠팡은 공격자 기기에서 저장된 자료 약 3천 건을 발표했고, 정부는 무단 조회된 개인정보를 기준으로 더 큰 유출 범위를 판단했다. 저장 건수와 유출·조회 건수는 서로 다른 지표이므로 단순 배수 비교로 고의 축소를 단정할 수 없다.
- **자료 보전 명령 미이행**: 보전 명령에도 일부 접속 기록이 삭제돼 침투 경위 규명이 어려워졌고, 수사 의뢰로 이어졌다.
- **72시간 신고 지연**: 개인정보위는 추가로 인지한 약 16만 명의 유출을 관계 당국에 72시간 내 신고하지 않았다고 밝혔다. [개인정보위](https://pipc.go.kr/eng/user/ltn/new/noticeDetail.do?bbsId=BBSMSTR_000000000001&nttId=3071)
- **부실한 자체 조사**: CPO를 배제한 채 해커 진술에만 의존한 결과를 공개해 사회적 혼란을 키웠다.

## 9. 재발 방지책과 교훈

**개발자 관점** — 비밀 값(서명키·API 키·DB 접속정보)은 소스코드에서 분리해 Secret Manager에 보관하고 정기적으로 교체. 커밋 전 시크릿 스캐닝 도구로 하드코딩을 차단.

**보안·운영 관점** — 인증은 토큰 하나에 의존하지 말고 세션·디바이스·행위 기반 검증을 겹치기. 퇴사자 오프보딩 시 노출 가능성이 있는 키의 영향 범위를 확인하고 안전하게 교체. 비정상 대량 조회를 잡는 이상 행위 탐지(UEBA)를 상시 가동.

**조직·대응 관점** — 적용되는 신고·통지 의무와 기한을 확인하고, CPO와 포렌식 전문가가 사실 확인에 참여하도록 한다. 확인된 범위와 아직 조사 중인 범위를 구분해 안내한다.

### 2. 정상 인증과 위조 인증의 차이

정상 흐름에서는 사용자가 로그인한 뒤 서비스가 인증 정보를 발급하고, 이후 관문 서버가 그 정보를 검증해 요청을 처리한다. 이때 서명 검증은 **토큰이 해당 키로 서명됐는지**를 확인하는 수단이다. 서명키 자체가 노출되면 공격자도 유효한 서명을 만들 수 있으므로, 서명이 맞는지만으로 토큰의 정상 발급 여부를 구별하기 어려워진다.

정부 조사에 따르면 공격자는 재직 중 관리하던 서명키를 부정하게 확보했고, 퇴사 후 이를 이용해 다른 이용자의 전자 출입증을 위조했다. 쿠팡은 퇴사 후 해당 키를 즉시 갱신·폐기하지 않았다. 조사단은 위조 출입증을 탐지·차단할 검증 체계가 부족했다고 설명한다. 이는 단순히 퇴사자 계정을 비활성화하는 것만으로, 이미 알려진 공통 서명키의 위험이 사라지지 않는다는 사례다. [과기정통부 원인 분석](https://www.msit.go.kr/eng/bbs/view.do?bbsSeqNo=42&mId=4&mPid=2&nttSeqNo=1221&sCode=eng)

### 3. 한 가지 실수가 아니라 여러 통제의 실패

**키 보관과 수명:** 개인정보위는 필요하지 않은 상황에서도 대체 서명키에 평문으로 접근할 수 있었고, 공격자 퇴사 후 키를 즉시 갱신·폐기하지 않았다고 밝혔다. 과기정통부는 재직 개발자 노트북에서 하드코딩을 통한 로컬 저장도 확인했다. 다만 공격자가 어떤 특정 파일에서 키를 얻었는지는 별도 사실로 입증해야 한다.

**발급 이력 검증:** 유효한 서명과 정상 발급은 동일하지 않다. 서버 측 발급 이력이나 세션 상태를 확인하는 설계, 키 사용 범위 분리, 짧은 수명의 인증 정보 등은 피해 범위를 제한하는 방안이 될 수 있다. 각각의 효과와 비용은 서비스 구조에 따라 검토해야 한다.

**이상 행위 대응:** 개인정보위는 개인정보 페이지에서 트래픽 이상이 발생했지만 차단 임계값 설정과 별도 분석이 충분하지 않았다고 판단했다. 많은 조회가 자동으로 모두 악성인 것은 아니므로, 계정·기기·IP·페이지별 요청과 시간대 패턴을 결합해 조사해야 한다. 공격자가 여러 IP를 사용한 점도 단일 IP 차단에만 의존하기 어려운 이유다. ### 4. 사고 대응과 제재를 구분해 읽기

과기정통부는 쿠팡이 사고를 2025-11-17 인지하고 11-19 KISA에 신고했다고 밝혔다. 또 같은 날 자료 보전 명령 이후 웹·애플리케이션 접근 기록이 삭제돼 조사를 방해했다고 발표했다. 개인정보위는 별도로 약 16만 명의 추가 유출에 대한 72시간 내 당국 신고 지연과 CPO의 자체 조사 배제 등을 문제로 판단했다. 두 기관의 신고·보전 관련 조치는 각각의 조사 범위와 법적 판단을 구분해야 한다.

### 5. 실무 적용: 예방부터 사고 이후까지

- **예방:** 서명키를 중앙 비밀 관리 체계에서 관리하고 접근자를 최소화한다. 코드·개발자 단말에 비밀이 남지 않도록 검사하고, 키별 책임자와 발급·폐기 이력을 유지한다.
- **퇴사·권한 변경:** 계정 회수와 별도로 해당 인력이 접근했거나 노출 가능성이 있는 키의 영향 범위를 조사하고 회전한다. 모든 키를 무조건 즉시 교체하기보다 서비스 의존성과 안전한 교체 절차를 준비한다.
- **탐지:** 토큰 발급 및 사용, 개인정보 페이지 접근, 비정상 요청량을 연결해 분석한다. 정당한 대량 작업과의 구분, 오탐 검토, 대응 담당자까지 설계해야 한다.
- **사고 대응:** 로그 보존을 즉시 설정하고, 유출 범위와 저장 범위의 정의를 분리해 기록한다. 개인정보 보호책임자와 법무·포렌식 담당자가 사실 확인과 신고 판단에 참여하도록 한다.

위 항목은 원문 조사 결과를 바탕으로 한 **재발 방지 제안**이며, 모두 사건 당시 이미 적용됐거나 정부가 개별적으로 명령한 조치라는 뜻은 아니다.
