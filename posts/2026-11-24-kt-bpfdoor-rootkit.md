## 1. TL;DR

- 과기정통부 민관합동조사단이 KT 서버를 점검한 결과 **94대 서버에서 BPFDoor·루트킷·DDoS 코드 등 악성코드 103종**이 확인됐다. 초기 침투는 인터넷에 노출된 서버의 **파일 업로드 취약점으로 웹셸을 올린 뒤 BPFDoor를 퍼뜨리는** 방식으로 추정된다.
- 핵심 악성코드인 **BPFDoor**는 리눅스 커널의 BPF(Berkeley Packet Filter)를 악용해, **포트를 열지 않고도** 특정 "매직 패킷"만 받아 명령을 수행하는 은닉형 백도어다. 프로세스 이름을 정상 시스템 프로세스로 위장하고, 메모리에 상주하며 흔적을 지운다. 탐지가 극히 어렵다.
- 기술적 침해 못지않게 **조직의 대응이 문제**였다. KT는 서버 대량 감염을 자체 파악하고도 당국에 신고하지 않고 은폐했고, 로그를 보존하지 않아 루트킷·백도어의 침투 경로조차 규명하지 못했다. "탐지의 실패"와 "은폐"가 겹친 사건이다.

## 2. 사건 개요

KT 침해사고 조사단은 KT 전체 서버를 여섯 차례 점검하고 감염 서버를 포렌식 분석해, **94대 서버에서 악성코드 103종 감염**을 확인했다. KT가 자체 보안점검에서 침해 흔적을 발견했다고 한 서버 및 연계 서버에 대한 조사단의 포렌식에서는 **53대 추가 감염**과 함께 루트킷 39종·백도어 36종·DDoS 공격형 2종 등 77종의 악성코드가 나왔다.

악성코드는 성격에 따라 침투 시점이 달랐다.

- **웹셸·BPFDoor**: 인터넷 접점 서버의 파일 업로드 취약점을 악용해 웹셸을 올린 뒤 확산한 것으로 추정. 추정 감염 기간 **2022-04-02 ~ 2024-04-19**.
- **루트킷·백도어**: 감염 당시 방화벽·시스템 로그가 남아 있지 않아 **침투 방법을 판단할 수 없었다**. 추정 감염 기간 **2023-03-11 ~ 2025-07-04**.

BPFDoor는 2025년 SK텔레콤 해킹 사태에서도 큰 피해를 준 악성코드로, 이번 KT 사건에서 다시 등장했다.

## 4. 배경 지식

### BPF(Berkeley Packet Filter)란

BPF는 리눅스·유닉스에서 네트워크 패킷을 커널 수준에서 필터링하는 기술이다. 원래는 `tcpdump` 같은 패킷 분석 도구나 보안·관측 도구가 쓰는 정상 기능이다. 문제는 악성코드가 이 기능을 역이용하면, **자기 포트를 열지 않고도 커널이 걸러준 특정 패킷만** 사용자 공간에서 받아볼 수 있다는 점이다.

### 웹셸 · 루트킷 · 백도어

- **웹셸(Web Shell)**: 웹 서버에 올려두는 악성 스크립트. 업로드에 성공하면 웹 요청만으로 서버에 명령을 내릴 수 있어, 흔히 **초기 침투 거점**으로 쓰인다.
- **루트킷(Rootkit)**: 자신과 다른 악성코드의 존재(프로세스·파일·네트워크 연결)를 시스템에서 숨기는 은닉 도구. 유저랜드형과 커널형이 있다.
- **백도어(Backdoor)**: 정상 인증을 우회해 공격자가 다시 들어올 수 있게 열어둔 뒷문.

## 5. 공격 흐름 분석 — KT 조사와 BPFDoor 공개 코드

정부 조사단은 일부 웹셸·BPFDoor 감염이 인터넷 접점 서버의 파일 업로드 취약점에서 시작해 확산됐다고 **추정**했다. 루트킷·백도어의 다른 감염 경로는 관련 로그가 남지 않아 확인하지 못했다. 아래 코드는 공개된 BPFDoor 소스 및 보안 연구의 분석 예시로, **KT에서 수거한 특정 파일의 코드라고 확인된 것은 아니다.** [정부 최종 브리핑](https://ebrief.korea.kr/briefing/67130) · [AhnLab 분석](https://asec.ahnlab.com/en/83925/)

### 5-1. 초기 침투: 파일 업로드와 웹셸

조사단의 추정 흐름은 인터넷에 노출된 서버의 파일 업로드 기능을 악용해 웹셸을 올리고, 이를 발판으로 악성코드를 확산시키는 것이다. 웹셸은 웹서버에서 실행되는 악성 스크립트로, 공격자가 후속 명령을 전달할 수 있는 통로가 된다.

다만 정부가 공개한 자료에는 **KT 취약 페이지의 소스코드, 정확한 업로드 요청, 업로드 검증 우회 방식**이 제시되지 않는다. 따라서 특정 확장자 우회나 파일 경로 조작이 실제 사용됐다고 덧붙이지 않는다. 개인정보위는 별도의 후속 조사에서 로밍렌탈서비스 홈페이지 취약점을 통한 침투와 SQL 삽입에 의한 일부 직원 정보 조회·유출 정황을 발표했다. [개인정보위 조사](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=12349)

### 5-2. 원시 소켓 생성과 필터 부착

공개 BPFDoor 코드에는 패킷 소켓을 만들고 필터를 연결하는 다음 호출이 있다. 이해에 필요한 부분만 발췌했으며 KT 샘플과 동일하다는 뜻은 아니다.

```c
socket(PF_PACKET, SOCK_RAW, htons(ETH_P_IP))
setsockopt(sock, SOL_SOCKET, SO_ATTACH_FILTER, &filter, sizeof(filter))
```

첫 호출은 IPv4 패킷을 관찰하는 원시 패킷 소켓 생성에 사용된다. 두 번째 호출은 미리 준비한 BPF 필터를 그 소켓에 연결한다. 이후 소스는 recvfrom으로 필터를 통과한 패킷을 읽는다. 이 단계는 애플리케이션용 TCP 포트에서 계속 listen하는 방식과 다르다. 소켓 생성에는 환경에 따른 권한이 필요하며 네트워크 방화벽을 자동으로 통과하는 것도 아니다. [공개 BPFDoor 코드](https://github.com/gwillgues/BPFDoor/blob/main/bpfdoor.c) · [MITRE Socket Filters](https://attack.mitre.org/techniques/T1205/002/)

### 5-3. 필터가 고르는 값과 패킷 파싱

AhnLab이 분석한 변종은 TCP에서 0x5293, UDP와 ICMP Echo Request에서 0x7255를 확인한다고 설명한다. 이 값은 모든 BPFDoor 변종의 공통값이 아니다. 공개 코드의 BPF 배열에도 TCP 매직 값에 해당하는 비교 명령이 포함돼 있으며, 수신된 패킷은 IP 프로토콜에 따라 TCP·UDP·ICMP 헤더를 건너뛰어 데이터 위치를 찾는다. [AhnLab 필터 분석](https://asec.ahnlab.com/en/83925/) · [공개 코드](https://github.com/gwillgues/BPFDoor/blob/main/bpfdoor.c)

```text
네트워크에서 패킷 도착
  → 원시 소켓에 부착된 BPF 조건 확인
  → 조건에 맞는 패킷을 프로세스가 수신
  → 프로토콜별 헤더를 해석해 데이터 위치 확인
  → 패킷의 인증 정보에 따라 후속 동작 분기
```

여기서 매직 값은 **백도어 활성화를 위한 필터 조건**이지, KT 사건에서 실제로 캡처된 패킷 값이라고 확인된 것은 아니다. 방어에서는 이 값만 찾는 규칙에 의존하기보다 원시 소켓·필터 부착과 후속 프로세스 행위를 함께 본다.

### 5-4. 프로세스 위장과 원격 제어

공개 코드의 set\_proc\_name 함수는 프로세스 인자 영역을 덮어쓰고 prctl의 PR\_SET\_NAME을 호출한다. AhnLab도 분석 샘플의 정상 프로세스명 위장을 설명한다.

```c
prctl(PR_SET_NAME, (unsigned long) new);
```

이름만 확인하면 정상 데몬처럼 보일 수 있으므로 실행 파일 경로, 프로세스 시작 이력, 소켓과 부모 프로세스까지 대조해야 한다. 이름 위장이 곧 커널 루트킷을 의미하는 것은 아니다. [공개 코드](https://github.com/gwillgues/BPFDoor/blob/main/bpfdoor.c) · [AhnLab](https://asec.ahnlab.com/en/83925/)

공개 샘플의 후속 분기에는 리버스 셸과 바인드 셸이 있다. 리버스 셸은 감염 서버가 외부로 연결하고, 바인드 셸은 일시적으로 포트를 열어 들어오는 연결을 받는다. AhnLab이 분석한 사례에서는 바인드 셸을 위해 iptables 리다이렉트 규칙을 추가·삭제한다. **대기할 때 포트를 계속 열지 않는다는 설명과 후속 단계에서 포트를 일시 개방한다는 설명은 양립한다.**

### 5-5. 조사와 탐지에 활용할 점

- 원시 패킷 소켓을 연 프로세스와 BPF 필터 부착을 추적하고 정상 패킷 분석 도구의 사용 이력과 비교한다.
- 프로세스 이름과 실행 파일 경로, 삭제된 실행 파일, 시작 시각, 부모 프로세스 관계를 함께 확인한다.
- 방화벽 규칙 변경이나 패킷 수신 직후의 예기치 않은 외부 연결을 상관 분석한다.
- 웹 접근·업로드·시스템·방화벽 로그를 외부에 보존해 웹셸 업로드 추정과 실제 실행 시점을 대조한다.

어느 지표 하나만으로 BPFDoor 감염이라고 단정할 수 없다. 이 절의 코드는 공개 샘플 분석이고, KT 사고의 확정 사실은 정부 포렌식 결과와 구별해 읽어야 한다.

## 6. 근본 원인 분석

### 코드로 보는 원인: 업로드된 파일이 실행 가능한 영역에 놓이는 위험

정부 조사단은 인터넷 접점 서버의 **파일 업로드 취약점을 통한 웹셸 업로드와 BPFDoor 확산**을 추정했다. 다만 KT의 실제 업로드 처리 소스코드, 파일 저장 경로, 검증 우회 방식은 공개된 조사 결과에서 확인되지 않는다. 아래는 웹셸 위험이 어떻게 생길 수 있는지 설명하는 별도 예시이며 KT의 실제 코드가 아니다. [정부 최종 조사](https://ebrief.korea.kr/briefing/67130)

```python
# 설명용 예시: 실제 KT 소스코드 아님
def upload(request):
    file = request.files["file"]
    file.save("/var/www/public/uploads/" + file.filename)
    return "uploaded"
```

이 코드는 사용자가 제공한 이름으로 파일을 웹 공개 디렉터리에 저장한다. 만약 해당 디렉터리에서 서버가 업로드된 스크립트 확장자를 실행하도록 설정돼 있고 공격자가 그 형식의 파일을 올릴 수 있다면, 업로드와 이후 웹 요청이 결합해 서버 명령 실행으로 이어질 수 있다. **파일 저장만으로 항상 웹셸 실행이 되는 것은 아니며**, 실제 위험은 서버 실행 설정, 업로드 권한, 파일명 처리 등 조건에 달려 있다.

이 예시로부터 KT에서 특정 확장자 우회, 경로 조작, 위 함수와 같은 구현이 사용됐다고 추론해서는 안 된다. 공개 조사에서 확인할 수 있는 수준은 위와 같은 초기 침투 경로의 추정이다.

### 저장 경계와 실행 경계를 분리하는 설계 예시

```text
# 설명용 의사코드: 실제 KT 수정 코드 아님
require_authorized_user(request)
enforce_size_limit(file)
validate_file_against_business_allowlist(file)
store_with_random_id_outside_webroot(file)
scan_or_quarantine_before_use(file)
serve_as_non_executable_content_only(file)
```

여기서 핵심은 확장자 한 번 확인하는 데 그치지 않고, **인가·파일 크기·허용 형식·격리·저장 위치·실행 권한**을 함께 설계하는 것이다. 업로드 파일을 웹서버가 스크립트로 실행하지 못하게 하고, 파일명을 그대로 신뢰하지 않으며, 안전한 다운로드 경로를 별도로 둔다. 검증·격리는 파일 형식과 운영 환경에 맞게 구현해야 한다.

BPFDoor의 패킷 소켓과 프로세스 위장 코드는 5절에 실제 공개 샘플 발췌로 제시했다. 그것은 **침투 이후 백도어 동작**을 설명하는 코드이며, KT 웹 업로드의 실제 취약 소스코드나 최초 감염 경로를 입증하는 코드는 아니다. [AhnLab 공개 샘플 분석](https://asec.ahnlab.com/en/83925/)

### 6-1. 기술적 원인

- **초기 침투 표면**: 조사단은 인터넷 접점 서버의 파일 업로드 취약점을 이용한 웹셸 업로드와 일부 악성코드 확산을 추정했다. 모든 감염의 경로가 확인된 것은 아니다.
- **은닉형 위협 탐지 공백**: 포트를 열지 않고 프로세스를 위장하는 BPFDoor 특성상 전통적 탐지(포트·시그니처)로는 잡기 어려웠고, 이를 보완할 행위 기반·커널 수준 탐지가 부족했다.
- **로그 미보존**: 루트킷·백도어 감염 당시 방화벽·시스템 로그가 남지 않아, 침투 경로 자체를 규명할 수 없었다. 이는 포렌식 대응의 전제가 무너진 것이다.

### 6-2. 관리적·조직적 원인

- **감염 사실 은폐**: 서버 대량 감염을 자체 파악하고도 당국에 신고하지 않았다. 정보통신망법상 침해사고 신고 지연·미신고는 과태료 대상이다.
- **보안 거버넌스 분산**: 정보보호최고책임자(CISO)가 전사를 총괄해야 하나, 보안 업무가 IT 부문·네트워크 부문·정보보안실로 쪼개져 있어 통합 대응이 어려웠다.

## 8. 미흡했던 점

- **탐지 공백**: 조사단은 여러 시기에 걸친 감염을 추정했지만 모든 악성코드가 2년 넘게 연속 상주했다는 의미는 아니다.
- **은폐**: 정부에 신고하지 않고 자체 조치해 외부 조사와 피해 범위 확인이 어려워졌다. 미신고로 인한 구체적 추가 피해 규모는 확인되지 않았다.
- **로그·증거 보존 부재**: 핵심 로그가 없어 루트킷·백도어의 침투 경로를 끝내 규명하지 못했다. 사후 분석이 불가능해진 가장 뼈아픈 지점.
- **거버넌스 분산**: 보안 책임이 조직별로 흩어져 전사 차원의 신속 대응이 어려웠다.

## 9. 재발 방지책과 교훈

**탐지·엔지니어링 관점** — 포트·시그니처 중심 탐지만으로는 BPFDoor 같은 포트리스 백도어를 잡을 수 없다. **AF\_PACKET 소켓 생성, BPF 필터 부착, 프로세스 이름 위장** 같은 커널·행위 기반 지표를 상시 모니터링. 리눅스 서버용 EDR 도입.

**로그·포렌식 관점** — 방화벽·시스템 로그를 **서버와 분리된 중앙 저장소**에 장기 보존. 로그가 없으면 사후 원인 분석 자체가 불가능하다는 것을 이 사건이 보여준다.

**거버넌스·대응 관점** — 침해사고는 은폐가 아니라 **즉시 신고**가 원칙. CISO에게 전사 보안을 총괄하는 실질 권한(예산·인력·이사회 보고)을 부여해 분산된 책임 구조를 통합.

## 심화 분석: KT 조사 결과와 BPFDoor 분석의 경계

### 1. 94대와 103종은 어떻게 집계됐는가

민관합동조사단은 KT가 관리하는 약 3만 3천 대의 서버를 여섯 차례 점검하고 감염 서버를 정밀 분석했다. 최종 발표에서 악성코드 감염 서버는 총 94대, 확인된 악성코드는 총 103종이었다. 이 숫자는 아래 두 조사 묶음의 합이다.

| 조사 묶음 | 서버 | 악성코드 | 발표 내용 |
| --- | --- | --- | --- |
| 2024년 KT가 자체 조치한 감염 | 41대 | 26종 | BPFDoor 4종, 웹셸 16종, 원격제어형 6종 |
| 외부 보안점검에서 침해 흔적이 발견된 서버와 연계 서버 | 53대 | 77종 | 루트킷 39종, 백도어 36종, DDoS 공격형 2종 |
| 전체 | 94대 | 103종 | 서버 수와 악성코드 종류 수를 합산한 조사 결과 |

**94대가 모두 BPFDoor에 감염됐거나, 103종 모두가 같은 공격자가 사용한 하나의 악성코드라는 뜻은 아니다.** 감염 시기·유형·침투 경로도 구분해야 한다. [정부 최종 브리핑](https://ebrief.korea.kr/briefing/67130)

### 2. 확인된 경로, 추정된 경로, 미확인 경로

2025년 최종 조사단은 웹셸·BPFDoor 계열에 대해 인터넷 접점 서버의 파일 업로드 취약점을 이용해 웹셸을 올린 후 확산됐다고 **추정**했다. 반면 별도의 루트킷·백도어 감염은 당시 방화벽·시스템 로그가 남아 있지 않아 침투 방법을 판단할 수 없었다. 하나의 경로를 94대 전체에 적용해서는 안 된다.

개인정보위의 2026년 후속 조사에서는 2024년 3월 로밍렌탈서비스 홈페이지의 취약점을 통한 침투와 악성파일 업로드, 관리자 페이지에 대한 SQL 삽입 공격을 통한 일부 직원·협력사 정보 조회·유출 정황을 발표했다. 위원회의 해당 네트워크 조사 대상은 38대다. 과기정통부가 발표한 41대 가운데 3대는 별도 네트워크에 있고 개인정보처리시스템에 해당하지 않아 조사 대상에서 제외됐기 때문이다. **38대, 41대, 94대는 조사 범위가 서로 다르다.** [과기정통부](https://ebrief.korea.kr/briefing/67130) · [개인정보위](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=12349)

### 3. BPFDoor가 포트 중심 점검을 피하는 원리

일반적으로 서버 프로그램은 특정 TCP·UDP 포트에서 요청을 기다린다. 관리자는 리스닝 포트 목록을 확인해 예상하지 못한 서비스를 찾을 수 있다. BPFDoor의 공개 분석 사례에서는 악성 프로세스가 패킷 소켓에 BPF 필터를 연결해 특정 조건의 패킷을 감시한다. 그러므로 **대기할 때 별도의 리스닝 포트를 계속 열어두지 않을 수 있다.**

필터에 맞는 신호가 도착하면 악성코드가 후속 명령을 처리한다. 분석된 변종에는 공격자에게 역방향으로 연결하거나, 일시적으로 포트를 열고 방화벽 규칙을 조작하는 방식이 있다. 따라서 포트가 전혀 열리지 않는다고 일반화해서도 안 된다. 호스트에 패킷이 도달하려면 외부 네트워크와 방화벽 조건도 만족해야 한다. [AhnLab 분석](https://asec.ahnlab.com/en/83925/) · [MITRE T1205.002](https://attack.mitre.org/techniques/T1205/002/)

앞서 적은 매직 값, 위장 프로세스명, 응답 방식은 **공개된 BPFDoor 샘플의 분석 결과**다. 변종은 서로 다를 수 있고 정부 발표만으로 KT의 각 샘플이 그 값을 모두 사용했다고 확인할 수 없다. 악성코드 계열의 일반 동작을 설명하는 자료와 사건 현장에서 실제로 관찰한 증거는 분리해야 한다.

### 4. 탐지와 포렌식에서 무엇이 문제였나

정부는 일부 감염 서버에 개인정보가 있었으나, 로그가 남은 기간의 정밀 분석에서는 유출 정황이 없었다고 발표했다. 동시에 시스템 로그 보관 기간이 1~2개월에 불과하고 일부 보안 장비가 부족해 **기록이 없는 기간의 유출 여부는 확인할 수 없었다.** 이는 유출이 없었다는 증명도, 있었다는 증명도 아니다. 이후 개인정보위는 별도 조사 범위에서 일부 직원·협력사 정보 조회·유출 정황을 발표했다. 두 결과는 조사 시점과 대상을 함께 봐야 한다. [정부 발표](https://ebrief.korea.kr/briefing/67130) · [개인정보위 후속 조사](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=12349)

대응 관점에서 포트 목록과 악성 파일 이름만 보는 점검은 부족할 수 있다. 원시 소켓과 BPF 필터를 사용하는 프로세스, 실행 파일 경로와 프로세스 이름의 불일치, 비정상 방화벽 규칙 변경, 신호 패킷 이후의 외부 연결을 함께 살펴야 한다. 정상 모니터링 도구도 비슷한 기능을 사용하므로 단일 지표만으로 악성이라고 결론 내리지 않는다.

### 5. 조직 대응과 재발 방지

개인정보위는 KT가 2024년 3월 감염을 인지하고도 정부에 신고하지 않은 채 자체 조치했으며, 이후 로그 삭제와 조사 과정의 거짓 자료 제출 등 조사 방해 사실이 있다고 발표하고 고발을 의결했다. 이는 기관의 조사·처분 내용이며 이후 사법 절차의 결과를 뜻하지는 않는다. [개인정보위 발표](https://pipc.go.kr/np/cop/bbs/selectBoardArticle.do?bbsId=BS074&mCode=C020010000&nttId=12349)

재발 방지를 위해서는 다음을 함께 적용할 수 있다.

1. **공격 표면 축소:** 인터넷 접점의 파일 업로드 기능과 권한, 취약한 웹 애플리케이션, 서버 간 이동 경로를 점검한다.
2. **서버 행위 감시:** 보안 담당자가 원시 소켓·BPF 필터·프로세스 위장·방화벽 변경을 상관 분석할 수 있게 한다. 변종별 특성은 위협 정보로 갱신한다.
3. **증거 보존:** 시스템·인증·방화벽 로그를 서버 외부로 전송하고, 보관 기간·무결성·접근 권한을 정한다. 사고 인지 시 자동 삭제를 중지하고 원본을 보전한다.
4. **신고와 의사결정:** 침해 의심의 내부 보고 경로와 관계기관 신고 판단 절차를 정하고, 조사 기록과 의사결정 근거를 남긴다.
5. **복구 검증:** 악성 파일 제거만으로 종료하지 않고 초기 침투 경로, 계정·키 노출, 지속성, 연결 서버의 감염 여부까지 점검한다.

이 항목들은 사건에서 얻은 **재발 방지 제안**이다. 조직별 적용 시 개인정보의 민감도와 법령·계약상 보관 의무를 따로 확인해야 한다.
